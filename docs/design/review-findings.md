# Review pass — findings and what was decided

52 findings raised across 7 reviewers; 40 survived verification. Roughly one in four was refuted
or overstated, which is why everything here was reproduced before being acted on.

Every `fix_now` and `fix_later` item below has landed. **The `set_aside` section is the valuable
part now** — it records what was examined and deliberately not changed, with the measurement
behind each decision. Do not undo those without new evidence.

## Fixed — shipped in v0.9.0

- **`pipe.rs` / `pipe_dispatch.rs` gated the post-action read on a baseline already existing.** `baseline` is `None` when `last_snapshot` is `None`, so `attach_change_report` never runs, so `last_snapshot` is never written, so the session never bootstraps — the branch's flagship feature silently off for the whole session in 2 of 3 modes. Verified live: 3 clicks each adding a heading, zero `changed`/`delta`; add one `{"cmd":"inspect"}` and all 3 report. Fix: call the read whenever `report.changes && mutates_page(cmd)`, pass the old text as `Option<&str>`, always store the fresh snapshot — as the CLI already did. Both parity tests ran an explicit inspect first, which is why it shipped.

- **`press` derived `windowsVirtualKeyCode` from `ch.to_ascii_uppercase() as u8`**, so punctuation carried an editing/navigation key code. Verified live in a focused input seeded "XYZ": `press .` → field becomes "YZ" (46 = VK_DELETE), `ok:true`. `' $ % & # (` insert nothing and silently move the caret; `press Į` (low byte 0x2E) also deletes. `, ! - / a 5 [` are fine. Fix: claim a code only where the ASCII mapping is real — `if ch.is_ascii_alphanumeric() { … } else { 0 }`; the existing `if vk_code > 0` guard drops the field and Chrome inserts from `text` alone. A US-layout punctuation table would be better still. Silent data loss reported as success. Note: keyUp carries no vk code for any key, Enter included.

- **`set_checked`'s `read_state` closure never called `check_js_exception`** while its sibling `set_checked_selector` did. A throwing probe yields `kind=""`, `refuse_uncheckable` passes, and the element is clicked anyway. Verified live on `<form><input name="type">` (DOM clobbering makes `el.type` an element, so `.toLowerCase()` throws): the uid path errored with "uid=n1 is still  after the click…" having dispatched a real click (`__clicked == 1`); the selector path on the same node returned a correct TypeError with no click. One line. It blamed the page for our own read failure AND mutated the page unrequested.

- **`set_checked_selector` probed, clicked and read back in one synchronous `Runtime.evaluate`**, so the read-back ran before any microtask or timer. Verified on the repo's own `#reverts` fixture: `check --selector "#reverts"` returned `ok:true` with the box `false` 300 ms later, while `check <uid>` correctly errored — the uid path won only by the incidental 50 ms of `wait_for_stabilization`. Fix: resolve the selector once to an `objectId` (no `returnByValue`), then drive `CHECKABLE_PROBE` / click / settle / probe via `Runtime.callFunctionOn`, sharing one settle window with the uid path.

- **`dispatch_fill_and_submit` ended in an unconditional `commands::read::run`**, so on any page Readability rejects, the whole command returned `{"ok":false,"error":"Page has minimal readable content…"}` after the fill and submit had landed. Verified: form submitted (`#st` reads "sent"), response says the command failed. An agent that retries a failed submit double-submits. Fix: make the trailing read best-effort — emit `content` on success, omit it or carry `read_error` otherwise, keep `ok:true` for the mutation that happened.

- **`type` had no focus precondition and no read-back**; the message was built from `text.len()`, i.e. from the request. Verified on both paths: `{"cmd":"type","text":"hello@example.com"}` with nothing focused → `Typed 17 chars`, `ok:true`, `activeElement` = BODY, field untouched; `type --selector "#marker"` at a `<p>` → `ok:true`, text unchanged — the agent named a target explicitly and got a false success. Fix: (a) one `Runtime.evaluate` before `Input.insertText` refusing when `document.activeElement` is null/BODY/HTML or not input/textarea/`isContentEditable`/`designMode`, naming what was focused; (b) `focus_selector` returns `document.activeElement === el` and refuses when false. Do NOT reuse `FillOutcome`'s verbatim-equality read-back: `insertText` inserts at the caret, so contenteditable legitimately yields `helloedit me`. Use contains-semantics and inherit the `sensitive` redaction.

## Fixed — shipped after v0.9.0

- **`run_form`, `dispatch_fill_form` and `dispatch_fill_and_submit` all discarded the `FillOutcome`.** For `fill-form` the delta covers the landed value, so the only unreachable signal is the `maxlength` caveat — precisely the case the delta cannot cover, because the value lands verbatim and looks perfect. For `fill_and_submit` the change report is attached after the submit, so the written values are already gone and the outcome is the only witness. Fix: collect the outcomes into a `values` array; filter to non-verbatim/caveat for `fill-form`, emit unconditionally for `fill_and_submit`. `fill_value_report` already handles redaction.

- **`scroll_collect`'s in-page promise re-armed a 400 ms debounce on every mutation with no hard deadline**, and `CdpClient::call` had no timeout, so a page mutating faster than 400 ms hung the call forever — in pipe mode wedging the whole persistent session with no error. Fix: replace the inline promise with `snapshot::settle(client, 400, 2000)`, whose hard timer is never cleared by a mutation; that also removes the flat 2 s charged per stale iteration on quiet pages. Add a wall-clock break for a renderer that stops answering entirely.

- **`click_selector` was `el.click()`** (synthetic, no pointerdown/mousedown, clicks through overlays) while `click <uid>` dispatched real `Input.dispatchMouseEvent` at box-model coordinates — the same unqualified success shape for two different physical actions, documented nowhere. Fix: mirror `dblclick_selector`, which had already made this rewrite: querySelector → scrollIntoView → getBoundingClientRect centre → `click_at_coords`, keeping `el.click()` only as the zero-box fallback. State the tradeoff: after the fix, `--selector` on a covered element hits the overlay, as it should.

- **The post-action `commands::inspect::run(...)?` propagated**, so a read-back failure turned a landed action into `{"ok":false}` + exit 1, while `pipe_dispatch.rs` stated the opposite policy in a comment and followed it. Fix: replace the `?` with a match that keeps `ok:true` and records why the report is absent. Rare in practice — not reachable with ordinary page behaviour — but the asymmetry is the defect.

- **Test coverage on the paths that just changed.** `checkable_kinds.html` carries `#reverts` ("Clicks through, then the app puts it back") and no test touched it; every test in `checkable_tests.rs` used `--selector` and `--verdict off`, so `set_checked` (uid) had zero coverage and the verdict mitigation was off in the one suite that would notice. `press_key_tests.rs` exercised only `h`, `i` and named keys, and `press_keys.html` logged only `e.key`, which Chromium echoes verbatim regardless of the vk code, so no test could observe the mapping. No test asserted non-JSON stdout. Minimum: `#reverts` through both targeting modes, `press .` asserting the seeded value was not shortened, and remove the explicit `{"cmd":"inspect"}` from `pipe_reports_changes_like_the_cli`.

- **`commands/record.rs` opened with `.create(true).append(true)` and no mode**, landing 0644 while screenshot, pdf, download and session all chmod 0600. Add a `cfg(unix)` `.mode(0o600)`. Note in the doc comment that chmod does not solve the real issue: the recording holds every command payload verbatim, including credentials, and `replay --var` is the mitigation.

## Set aside deliberately — do NOT "fix" without new evidence

- **`pipe.rs::dispatch` duplicating `pipe_dispatch::dispatch_single` arm-for-arm (~35 arms).** Real, but the failure mode is a loud `Unknown command: X` from one entry point, never a wrong answer, and the split has a technical driver: `dispatch_batch` calls `dispatch_single`, so a `batch` arm inside it is mutual async recursion that rustc rejects without boxing. The delegation fix is sound and would delete ~80 lines, but it is cleanup, not trust.

- **`resolve_uid`'s eager `DOM.getBoxModel` for callers that never read `.center`, and `set_checked` resolving the uid twice.** Measured at ~0.15 ms and 0.25% of a 159 ms command; the denominator is `settle(100,1000)` plus a full `getFullAXTree` the default verdict runs anyway. Worse, `center.is_none()` is the signal that routes click/dblclick to the JS fallback, so splitting the function edits the branch deciding whether a click is native or synthetic — to save 0.15 ms.

- **`session.rs` writing the temp file at umask perms before chmod 0600.** `save_to` chmods the parent to 0700 on every save before the write; without the execute bit no other user can open anything inside. The proposed `create_new(true)` fix is actively worse: it EEXISTs on a same-PID leftover, turning an unreachable perms nit into a permanent save failure.

- **Narrowing `snapshot::settle`'s MutationObserver to childList-only** to avoid the 1000 ms ceiling on animated pages. A reviewer built and measured the patch: on a React-shaped fixture committing text via `nodeValue`, the shipped code reports the final `"Result: 42 items"` and the narrowed version reports the intermediate `"Loading.."`. It trades a latency cost for a wrong-answer cost, which is backwards for this tool. Document the worst case and leave `--verdict off` as the escape hatch.

- **Resolving probes and read-back in an isolated world** so a hostile page cannot forge `verbatim` / `Already checked`. The forgery reproduces, but it is byte-identical to v0.8.0 (the old `set_checked` read `!!this.checked` in the main world too), and an isolated world does not fix the weaker link: a page that gives its decoy `id="real"` defeats it completely. If this area is worth hardening, resolve `--selector` via CDP `DOM.querySelector` instead — that kills the redirect for every action, cheaply. File separately.

- **Capping `last_snapshot` size, or calling `cleanup_stale` from `load_session`.** Capping breaks the diff outright: every uid past the cut is absent from `old_by_uid` and emitted as `+ added`, i.e. hundreds of phantom additions. `cleanup_stale` on load puts a blocking 500 ms ureq probe on every CLI command and can evict a live parallel agent's baseline on one transient failure. Measured cost of the thing being optimised: ~5 ms per MB.

- **SKILL.md's duplicated ordinals 13/14/15, the dead alias entries in `mutates_page` (`navigate`/`open`/`go`/`tap`/`double_click`), and the 12 copies of `chrome_available()`.** All cosmetic or loud-failing. The one thing worth taking from that cluster is orthogonal: make CI fail on `SKIP: Chrome not found` rather than mirroring `browser.rs`'s candidate list. A skipped suite is currently indistinguishable from a passing one, which is a larger silent-pass surface than any of them.

## Mission gaps — all addressed

- **Silence meant four different things and the agent could not tell them apart.** A response with no `changed`/`delta` was emitted for `--verdict off`, no baseline stored, a failed post-action read, and genuinely nothing changed. Three are "I don't know" and one is an assertion. A `verdict` field with a `verdict_reason` on the unavailable branch is the smallest change that stops an agent reading "I couldn't look" as "nothing happened".

- **`press` and `type` asserted success about the request, never about the page.** Every other mutating action grew a read-back; these two did not, and both are documented as the fallback for cases `fill` cannot handle (contenteditable). `ok:true` from them stated that a CDP message was accepted, which is not what the agent is asking.

- **There was no stated observation horizon.** The read-backs saw 0 ms (`check --selector`), ~50 ms (`check <uid>`, by accident) and 100–1000 ms (the verdict settle). A revert scheduled past the window was reported as success in every path, and the repo's own `form_value_late_revert.html` (400 ms) escaped all of them. The docs promised "the state is read back" with no qualification. Either the docs name the window, or the agent has to assume the tool is omniscient.

- **Targeting was unverifiable.** `--selector` resolves through in-page `document.querySelector`, the message names the selector, the delta names a uid, and nothing bound the two. Echoing the resolved uid in every selector-path action response makes the delta cross-checkable and costs one field.

- **`CdpClient::call` had no timeout anywhere.** Every other long operation wraps CDP in `tokio::time::timeout` or races an in-page deadline, but the primitive itself was unbounded, so any in-page promise that never resolves wedges a pipe session permanently with no error and no recovery. `inspect --limit` was the reachable instance; it is not structurally the only one.

- **Two clicks, one name.** `click <uid>` dispatched trusted mouse events with hit-testing; `click --selector` called `el.click()`, which fires no mousedown and passes straight through a covering modal. Both returned the same success shape. Same for the `submit` inside `fill_and_submit`, which routes through `click_selector`.

- **The test harness could not fail loudly.** `chrome_available()` false → bare `return` → green, across ~57 of 68 tests; `fill_on`/`open` return `None` on a failed `goto` → the test returns and passes; `fixture_url` never asserted the path exists. Deleting a fixture, or losing Chrome on the runner, turned the whole E2E suite into a silent no-op. For a tool whose entire claim is browser-observed behaviour, coverage that can silently go to zero is the gap behind several of the findings above.
