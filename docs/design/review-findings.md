# Review pass — findings and what was decided

Rescued from a workflow output under `/tmp`. 52 findings raised across
7 reviewers, 40 survived verification — roughly one in four was
refuted or overstated, which is the reason everything here was reproduced before being
acted on.

Status as of this commit: every `fix_now` and every `fix_later` item below has landed.
The `set_aside` section is the valuable part now — it records what was examined and
deliberately not changed, with the measurement behind each decision. Do not undo those
without new evidence.


## Fixed — shipped in v0.9.0

- src/pipe.rs:205-217 + :277 and src/pipe_dispatch.rs:696-708 + :762 — stop gating the post-action read on a baseline already existing. `baseline` is `None` when `last_snapshot` is `None`, so `attach_change_report` never runs, so `last_snapshot` is never written, so the session never bootstraps. Call the read whenever `report.changes && mutates_page(cmd)`, pass the old text as `Option<&str>`, and always store the fresh snapshot — the CLI already does exactly this at run_helpers.rs:221-228. Cannot wait: this is the branch's flagship feature, silently off for the entire session in 2 of 3 modes. Verified live — 3 clicks each adding a heading, zero `changed`/`delta`; add one `{"cmd":"inspect"}` and all 3 report. CLAUDE.md:66 says 'default on, all three modes'; SKILL.md:29 says 'you don't need a second call to find out'. It is also the reason findings 3 and 5 below are silent rather than merely contradictory. Both parity tests (tests/action_report_tests.rs:76 and :136) run an explicit inspect first, which is why it shipped.

- src/element.rs:345-348 — `press` derives `windowsVirtualKeyCode` from `ch.to_ascii_uppercase() as u8`, so punctuation carries an editing/navigation key code. Verified live in a focused input seeded 'XYZ': `press .` → field becomes 'YZ' (46 = VK_DELETE), `ok:true`. `' $ % & # (` insert nothing and silently move the caret (39/36/53→37/38/35/40), `ok:true`. `press Į` (low byte 0x2E) also deletes. `, ! - / a 5 [` are fine. Fix: only claim a code where the ASCII mapping is real — `if ch.is_ascii_alphanumeric() { u32::from(ch.to_ascii_uppercase() as u8) } else { 0 }`; the existing `if vk_code > 0` guard drops the field and Chrome inserts from `text` alone. A US-layout punctuation table is better still. Cannot wait: silent data loss reported as success, on a path SKILL.md:238 now advertises ('press types single characters'). While there, keyUp (element.rs:379-386) carries no vk code for any key, Enter included.

- src/element_controls.rs:174-183 — `set_checked`'s `read_state` closure maps only the transport error and never calls `check_js_exception`, while its sibling `set_checked_selector` does at :238. A throwing probe yields `kind=""`, `refuse_uncheckable` passes, and the element is clicked anyway. Verified live on `<form><input name="type">` (DOM clobbering makes `el.type` an element, so `.toLowerCase()` throws): uid path → `{"error":"uid=n1 is still  after the click..."}` with a real click dispatched (`__clicked == 1`); selector path on the same node → correct TypeError, no click. One line: chain `check_js_exception` inside the closure. Cannot wait: it blames the page for our own read failure AND mutates the page unrequested.

- src/element_controls.rs:210-260 — `set_checked_selector` probes, clicks and reads back in one synchronous `Runtime.evaluate`, so the read-back runs before any microtask or timer. Verified live on the repo's own `#reverts` fixture: `check --selector "#reverts"` → `{"message":"Checked selector '#reverts'","ok:true}` with the box `false` 300 ms later; `check <uid>` on the same element correctly errors. The uid path only wins by the incidental 50 ms of `wait_for_stabilization`. Fix: resolve the selector once to an `objectId` (no `returnByValue`), then drive the existing `CHECKABLE_PROBE` / click / settle / probe via `Runtime.callFunctionOn` — that binds the node harder than today's comment claims and shares one settle window with the uid path. Cannot wait: SKILL.md:236 ships the guarantee ('They also read the state back after clicking') that this path does not deliver, and with the fix above still pending there is no delta to contradict it.

- src/pipe_dispatch_actions.rs:46 — `dispatch_fill_and_submit` ends in an unconditional `commands::read::run`, so on any page Readability rejects, the whole command returns `{"ok":false,"error":"Page has minimal readable content..."}` after the fill and the submit already landed. Verified live: form submitted (`#st` reads 'sent'), response says the command failed. An agent that retries a failed submit double-submits. Fix: make the trailing read best-effort — emit `content` when it succeeds, omit it (or carry a `read_error`) when it does not, and keep `ok:true` for the mutation that happened. Cannot wait: a false failure on a mutating command is the one shape that causes the agent to repeat the mutation.

- src/element.rs:295 (`type_text`) and src/element_selector.rs:170 (`focus_selector`) — `type` has no focus precondition and no read-back; the message is built from `text.len()`, i.e. from the request. Verified live, both paths: `{"cmd":"type","text":"hello@example.com"}` with nothing focused → `Typed 17 chars`, `ok:true`, `activeElement` = BODY, field untouched; `type --selector "#marker"` at a `<p>` → `Typed 5 chars into selector '#marker'`, `ok:true`, `activeElement` still BODY, text unchanged — the agent named a target explicitly and got a false success. Fix: (a) one `Runtime.evaluate` before `Input.insertText` refusing when `document.activeElement` is null/BODY/HTML or not input/textarea/`isContentEditable`/`designMode`, naming what was focused; (b) have `focus_selector` return `document.activeElement === el` and refuse when false. Cannot wait for the same reason as `press` — commit 00a2308 already decided this class for `press` ('refuse names we cannot send') and left `type` behind. Do NOT reuse `FillOutcome`'s verbatim-equality read-back: `insertText` inserts at the caret, so contenteditable legitimately yields `helloedit me`; use contains-semantics and inherit the `sensitive` redaction from bd272a4.


## Fixed — shipped after v0.9.0

- src/commands/fill.rs:16-27, src/pipe_dispatch_actions.rs:38 and :70 — `run_form`, `dispatch_fill_form` and `dispatch_fill_and_submit` all discard the `FillOutcome`. For `fill-form` the delta covers the landed value, so the only unreachable signal is the `maxlength` caveat — and that is precisely the case the delta cannot cover, because the value lands verbatim and looks perfect. For `fill_and_submit` the change report is attached after the submit, so the written values are already gone and the outcome is the only witness that exists. Collect the outcomes and emit a `values` array; filter to non-verbatim/caveat for `fill-form`, emit unconditionally for `fill_and_submit`. `fill_value_report` (run_helpers.rs:91) already handles redaction.

- src/commands/inspect.rs:56-75 — `scroll_collect`'s in-page promise re-arms a 400 ms debounce on every mutation with no hard deadline, and `CdpClient::call` (cdp/client.rs:135) has no timeout. A page mutating faster than 400 ms hangs the call forever; in pipe mode that wedges the whole persistent session with no error. This branch already added the right primitive: replace the inline promise with `snapshot::settle(client, 400, 2000)`, whose hard timer is never cleared by a mutation — that also removes the flat 2 s charged per stale iteration on quiet pages. Add a wall-clock `break` on the loop for a renderer that stops answering entirely.

- src/element_selector.rs:20-47 — `click_selector` is `el.click()` (synthetic, no pointerdown/mousedown, clicks through overlays) while `click <uid>` dispatches real `Input.dispatchMouseEvent` at box-model coordinates. Same unqualified success shape for two different physical actions, and nothing in CLAUDE.md/README/SKILL.md says so. Mirror `dblclick_selector` (:48-84), which already made exactly this rewrite and has a regression test at tests/cli_tests.rs:227: querySelector → scrollIntoView → getBoundingClientRect centre → `click_at_coords`, keeping `el.click()` only as the zero-box fallback. State the tradeoff: after the fix, `--selector` on a covered element hits the overlay, as it should.

- src/run_helpers.rs:154 — the post-action `commands::inspect::run(...)?` propagates, so a read-back failure turns a landed action into `{"ok":false}` + exit 1. src/pipe_dispatch.rs:785 states the opposite policy in a comment ('losing the report is a smaller problem than turning a successful action into an error') and the pipe path follows it. Replace the `?` with a match that keeps `ok:true` and records why the report is absent. Rare in practice — I could not reach it with ordinary page behaviour — but the asymmetry is the defect.

- Test coverage on the paths that just changed. tests/fixtures/checkable_kinds.html carries `#reverts` with the comment 'Clicks through, then the app puts it back' and no test touches it. Every test in tests/checkable_tests.rs uses `--selector` and `--verdict off`, so `set_checked` (uid) has zero coverage and the verdict mitigation is switched off in the one suite that would notice. tests/press_key_tests.rs exercises only `h`, `i` and named keys — no punctuation, and tests/fixtures/press_keys.html logs only `e.key`, which Chromium echoes verbatim regardless of the vk code, so no test can observe the mapping at all. No test anywhere asserts non-JSON stdout. Minimum: `#reverts` asserted through both targeting modes, `press .` asserting the seeded value was not shortened, and remove the explicit `{"cmd":"inspect"}` from `pipe_reports_changes_like_the_cli` so it guards the parity it claims.

- src/commands/record.rs:8-12 and :18-22 — both open with `.create(true).append(true)` and no mode; the file lands 0644 while screenshot.rs:105, pdf.rs:45, download.rs:150 and session.rs:159 all chmod 0600. Add a cfg(unix) `.mode(0o600)`. Low reach (`_record` is an undocumented per-command pipe field), and note in the doc comment that chmod does not solve the real issue — the recording holds every command payload verbatim, including credentials; `replay --var` is the mitigation.


## Set aside deliberately — do NOT "fix" without new evidence

- pipe.rs::dispatch duplicating pipe_dispatch::dispatch_single arm-for-arm (~35 arms). Real, but the failure mode is a loud `Unknown command: X` from one entry point — never a wrong answer — and the split has a technical driver: `dispatch_batch` calls `dispatch_single`, so a `batch` arm inside it is mutual async recursion that rustc rejects without boxing. The delegation fix is sound and would delete ~80 lines, but it is cleanup, not trust.

- resolve_uid's eager `DOM.getBoxModel` for callers that never read `.center`, and `set_checked` resolving the uid twice. Measured by a reviewer at ~0.15 ms and 0.25% of a 159 ms command; the denominator is `settle(100,1000)` + a full `getFullAXTree` that the default verdict runs anyway. Worse, `center.is_none()` is the signal that routes click/dblclick to the JS fallback, so splitting the function edits the branch deciding whether a click is native or synthetic — to save 0.15 ms.

- session.rs:151-162 writing the temp file at umask perms before chmod 0600. `save_to` chmods the parent to 0700 on every save before the write; without the execute bit no other user can open anything inside. The proposed `create_new(true)` fix is actively worse — it EEXISTs on a same-PID leftover and turns a non-reachable perms nit into a permanent save failure.

- Narrowing `snapshot::settle`'s MutationObserver to childList-only to avoid the 1000 ms ceiling on animated pages. A reviewer built the patch and measured it: on a React-shaped fixture committing text via `nodeValue`, the shipped code reports the final `"Result: 42 items"` and the narrowed version reports the intermediate `"Loading.."`. It trades a latency cost for a wrong-answer cost, which is backwards for this tool. Document the worst case and leave `--verdict off` as the escape hatch.

- Resolving probes/read-back in an isolated world so a hostile page cannot forge `verbatim`/`Already checked`. The forgery reproduces, but it is byte-identical to v0.8.0 (the old `set_checked` read `!!this.checked` in the main world too), and an isolated world does not fix the weaker link: a page that gives its decoy `id="real"` defeats it completely. If this area is worth hardening, resolve `--selector` via CDP `DOM.querySelector` instead (the pattern is already at element_controls.rs:315) — that kills the redirect for every action, cheaply. File separately, not against this branch.

- Capping `last_snapshot` size, or calling `cleanup_stale` from `load_session`. Capping breaks the diff outright — every uid past the cut is absent from `old_by_uid` and emitted as `+ added`, i.e. hundreds of phantom additions. `cleanup_stale` on load puts a blocking 500 ms ureq probe on every CLI command and can evict a live parallel agent's baseline on one transient failure. Measured cost of the thing being optimised: ~5 ms per MB.

- SKILL.md's duplicated ordinals 13/14/15, the dead alias entries in `mutates_page` (`navigate`/`open`/`go`/`tap`/`double_click`), and the 12 copies of `chrome_available()`. All cosmetic or loud-failing. The one thing worth taking from that cluster is orthogonal: make CI fail on `SKIP: Chrome not found` rather than mirroring browser.rs's candidate list — a skipped suite is currently indistinguishable from a passing one, which is a larger silent-pass surface than any of them.


## Mission gaps — all addressed

- Silence means four different things and the agent cannot tell them apart. A response with no `changed`/`delta` is emitted for: `--verdict off`, no baseline stored, the post-action read failed, and genuinely nothing changed. Three of those are 'I don't know' and one is an assertion. Nothing in the payload discriminates. A `verdict: "changed"|"unchanged"|"unavailable"` field with a `verdict_reason` on the unavailable branch is the smallest change that stops an agent reading 'I couldn't look' as 'nothing happened'.

- `press` and `type` assert success about the request, never about the page. Every other mutating action on this branch grew a read-back; these two did not, and both are documented as the fallback for cases `fill` cannot handle (contenteditable). `ok:true` from them is a statement that a CDP message was accepted, which is not what the agent is asking.

- There is no stated observation horizon. The read-backs see, respectively, 0 ms (check --selector), ~50 ms (check uid, by accident), and 100–1000 ms (the verdict settle). A revert scheduled past the window is reported as success in every path, and the repo's own `form_value_late_revert.html` fixture (400 ms) escapes all of them. CLAUDE.md:70 and SKILL.md:236 promise 'the state is read back' with no qualification. Either the docs name the window or the agent has to assume the tool is omniscient and it is not.

- Targeting is unverifiable. `--selector` resolves through in-page `document.querySelector`, the message names the selector, the delta names a uid, and nothing binds the two. An agent cannot ask 'which node did you actually act on'. Echoing the resolved uid in every selector-path action response would make the delta cross-checkable and would cost one field.

- `CdpClient::call` has no timeout anywhere (cdp/client.rs:135). Every other long operation in the repo wraps CDP in `tokio::time::timeout` or races an in-page deadline, but the primitive itself is unbounded, so any in-page promise that never resolves wedges a pipe session permanently with no error and no recovery path. `inspect --limit` is the reachable instance today; it is not structurally the only one.

- Two clicks, one name. `click <uid>` dispatches trusted mouse events with hit-testing; `click --selector` calls `el.click()`, which fires no mousedown and passes straight through a covering modal. Both return the same success shape, so an agent cannot know whether it interacted with the page a user could have. Same for the `submit` inside `fill_and_submit`, which routes through `click_selector`.

- The test harness cannot fail loudly. `chrome_available()` false → bare `return` → green, across ~57 of 68 tests; `fill_on`/`open` return `None` on a failed `goto` → the test returns and passes; `fixture_url` never asserts the path exists. Deleting a fixture, or losing Chrome on the runner, turns the whole E2E suite into a silent no-op. For a tool whose entire claim is browser-observed behaviour, coverage that can silently go to zero is the gap behind several of the findings above.
