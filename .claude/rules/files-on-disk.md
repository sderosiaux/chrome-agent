# Every file this tool writes, and how it gets there

Moved out of `CLAUDE.md`'s **Key Design Decisions** — not rewritten and not summarised. The
words are the ones that were there, minus the factual corrections made in the same change (a
path that had stopped resolving, a count that had gone stale). What changed is *when* they
load: this file is pulled in when you read a file its `paths:` block names, and costs nothing
in a session that touches none of them.

- **screenshot flags** — `--format jpeg`/`--quality`, `--max-width` (downscale via CDP `clip.scale`, no image crate), `--uid`/`--selector` clip via `DOM.getBoxModel` (`geometry::clip_for_*`). Never emits base64 on stdout.
- **`pdf`** — `Page.printToPDF` (`transferMode: ReturnAsBase64`) → shared `base64::decode` → 0600 file, mirrors screenshot.
- **`download <url>`** — in-page `fetch(url,{credentials:'include'})` → base64 in page → `base64::decode` → 0600 file. Auth-preserving. Filename from Content-Disposition (incl. RFC 5987 `filename*`) then URL.
- **A file the page builds has no URL, so `download` learned to click** (`src/commands/download_click.rs`, `commands::download::Target`) — `download <url>` could only reach a file with an address, which leaves out the half of the web where the bytes are made client-side (`URL.createObjectURL`) or served by a POST no anchor names: `inspect --urls` returns `blob:null/…`, and there is nothing to fetch. `download --uid n47` / `--selector "#export"` runs the click that already exists — `element::click` / `click_selector`, same hit test, same `--on-intercept`, same refusal messages, so a covered button reports its receiver here exactly as it does under `click` — and arms `Browser.setDownloadBehavior {behavior:"allowAndName", eventsEnabled:true}` around it. **Three things were measured before the shape was chosen.** (1) `Browser.*` is accepted on the PAGE websocket this tool already holds and `Browser.downloadWillBegin`/`downloadProgress` are delivered on it, so no second browser-level connection is needed. (2) The override does NOT outlive the CDP session that set it — a fresh connection clicking the same link with nothing armed produced no file at the armed path, the same rule `emulation.rs` documents for `Emulation.*`. That decides the shape: the arming has to happen on the connection that clicks, which is why this is a flag on `download` and not a separate `wait --download` verb — a separate verb works in pipe mode, where one connection spans both commands, and silently captures nothing from the CLI, where each invocation opens its own. (3) `Browser.cancelDownload` is implemented, so `--max-bytes` keeps one meaning across both halves of the verb instead of being declared inapplicable to this one. **`ok` is not the field to read, `downloaded` is.** A click that was delivered is never an error whatever it failed to produce, for the reason a lost transport is never a retry: the only recovery an error invites is a second click, and the page cannot tell that from a second deliberate action — on an export or a purchase that is two of them. So a click that landed and produced no file answers `ok:true`, `downloaded:false`, the window it waited (`observed_after_ms`) and a hint that forbids the retry in words, exactly as `fill` answers `ok:true` beside a `verbatim:false`. The one branch that permits a retry is the one where NOTHING was dispatched (`--on-intercept refuse`, an aim point that never settled): the page never saw an event, and its hint says so. **`download` stays out of `mutates_page`, and the reason is `goto`'s** — `landed` is self-describing and a `navigated` verdict on a command whose purpose is to navigate says nothing; `downloaded`/`path` are self-describing and a `no_effect` verdict on a command whose purpose is to produce a file would be worse than nothing, since a click that downloads a file usually leaves the accessibility tree identical. That is a `delivered_no_change` this command would report beside a 48 KB file on disk. The click's own evidence (`delivery`, `aim`, `uid`, `intercepted_by`) still rides on the response; `verdict_hint` is the one field stripped from it, because it names a vocabulary this response does not carry. **Four outcomes, four recoveries**: completed (the file, moved to `--out` or to the server's suggested name, 0600 like every other file this tool writes), never began, cancelled (by `--max-bytes`, or by Chrome), and still running when the window closed — the last two write nothing, because a prefix of a file is not the file. Chrome writes into a private `~/.chrome-agent/tmp/.incoming-<pid>-<nanos>/` so `allowAndName`'s guid-named files cannot collide with a concurrent agent's, and the sweep RETRIES: measured on the cancel path, Chrome answers `canceled`, we return, and it then finalises — recreating the directory and a zero-byte stub behind us. Same lesson as `close --purge`. One `--timeout` bounds both questions (did anything begin, did it finish) because the scale of the first is not knowable in advance: a blob begins in ~100 ms, an attachment begins when the server's response headers arrive, and a fixed short window would report "nothing began" for every slow server.
- **The sweep stopped running after Chrome** (`download_click::collect_abandoned`) — the retry above is bounded at 5 × 30 ms, and the entry that introduced it said "once per invocation" as if the cancel path were the only leak and 120 ms were enough for it. Both halves were wrong, and the second one turned red in CI: `transfer directories were left behind: [".incoming-17743-…"]`, on a pid the test had genuinely spawned. **Measured on the path the old entry never named** — a transfer still running when `--timeout` expires — with the shipped budget, eight downloads in a row: three directories were back on disk the moment the last invocation returned, and **all eight** were there fifteen seconds later, each holding the zero-byte stub `allowAndName` names after the guid. The reason is not a slow finalisation to wait out: **Chrome keeps the download after chrome-agent is gone**, so the only window wide enough is the length of the transfer, which is exactly the bound `--timeout` already declined to be. `disarm` does not help either — it is called before every `clean_up` already, and returning the *default* behaviour to Chrome says nothing about a transfer that has already chosen its path. Widening the budget would have moved the failure onto a slower runner, which is where it was found. **So the tool stops chasing Chrome and waits for the fact instead**: the directory is named after the process that armed it, only Chrome-on-behalf-of-that-invocation ever writes there, and the override dies with that CDP session — so a directory whose pid the OS no longer knows cannot gain another byte from anyone, and any later invocation may take it. `arm()` collects them before creating its own, through `session::liveness`, the same probe `profiles.rs` and the store prune read; this is `profiles.rs`'s shape, a removal predicated on "no live holder" rather than on a delay, and it converges without inventing a number. Verified end to end: the eight-out-of-eight scenario drains to zero on the next `download`. **Every unresolved case keeps the directory** — `Unknown` (a pid under another uid; and every non-Unix platform, where no probe is wired and this is a no-op), a name whose pid does not parse, and anything in `~/.chrome-agent/tmp` that is not a transfer directory, which matters because `screenshot`, `pdf` and `download <url>` put unnamed output in that same directory. A concurrent agent is safe by the predicate rather than by luck: its directory carries ITS pid, which reads `Alive`; a recycled pid reads `Alive` too and keeps a directory that could have gone, the harmless direction. **Arming is the collection point** because it is the only moment anyone has a reason to care, and the cost is measured: 227 µs with nothing to collect (every invocation after the first), 241 µs with 500 unrelated files beside it since the prefix filter answers before any pid is probed, 6.1 ms to drain a full 64-entry window. The save path where `profiles.rs` sweeps was the alternative and was rejected — it runs on every command including read-only ones, for a directory exactly one verb creates. Stated rather than hidden: a caller who abandons a download and never runs another keeps the crumbs, bounded at one partial file each. **The 5 × 30 ms sweep stays**, now as the fast path and not the guarantee: a completed download clears on the first attempt and never reaches the collector, so nothing routinely accumulates for a later invocation to find. **And the test became honest.** It used to demand no transfer directory of ours on disk within three seconds and poll for those three seconds without doing anything that could bring it about — nothing collected one of these except the invocation that opened it, and that invocation had exited. It now runs an arming invocation and asserts that nothing survives it, which is the promise the product actually makes: no partial file handed to the caller (asserted on the caller's own `--out` path) and nothing accumulating between invocations. The race itself is deliberately NOT reproduced — eight out of eight on a slow transfer, zero out of fifteen on a blob that finalises in milliseconds, so a test built on it is green on one machine and red on another, which is the failure mode this fixes. The state the race leaves behind is planted instead, and one test pins that arming is what collects it; verified by neutering the predicate, where seven of eight tests still passed and that one did not. A second defect surfaced on the way: the suite's `ours()` filtered by pid alone, which is process-global, so three tests failed at once on `.incoming-71509-…` and `.incoming-71525-…` — directories a SIBLING THREAD's slow transfer was still being written into. It now keys on the pid *and* the `TestBrowser` name, which is unique per test: the "a test owns what it names and nothing else" rule, one level in.
