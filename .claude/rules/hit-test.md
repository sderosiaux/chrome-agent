# Where a pointer event lands, before it is dispatched

Moved out of `CLAUDE.md`'s **Key Design Decisions** — not rewritten and not summarised. The
words are the ones that were there, minus the factual corrections made in the same change (a
path that had stopped resolving, a count that had gone stale). What changed is *when* they
load: this file is pulled in when you read a file its `paths:` block names, and costs nothing
in a session that touches none of them.

- **`click --selector` is the same verb as `click <uid>`** — both resolve the element's viewport centre and dispatch native CDP input (mouse normally, or a touch tap under `--touch`) (`element_selector::click_selector`, mirroring `dblclick_selector`). It used to call `el.click()`, which fires the handler whatever is stacked above the node: a click on a button under a modal scrim reported success with the same shape as a click a user could have made, and nothing in the response distinguished the two spellings. Consequence, deliberate: a covered element now hands the click to whatever covers it — `--selector` on a button behind a cookie banner clicks the banner, which is what a pointer does, and since the hit test the response says so instead of leaving the caller to notice. The JS `click()` survives only as the zero-size fallback, where there is no point to aim at.
- **A pointer-targeted action measures where it will land before it dispatches** (`src/hit_test.rs`, `--on-intercept`) — one `Runtime.callFunctionOn` bound to the target's `objectId` scrolls it into view, takes the centre of its LARGEST client rect, maps that through the frame chain into top-level coordinates, and runs `elementFromPoint` there with shadow descent, `closest('label').control` retargeting and shadow-host containment. The response carries `delivery` (`target_hit` | `intercepted` | `off_target` | `not_settled` | `js` | `not_probed`), `aim`, and `intercepted_by {uid,tag,id,class,z_index,text,modal}`. **Which of the two interception reasons the field actually produces, and which field of `intercepted_by` carries the answer**: over 61 real sites across two audits, 8 interceptions, `hit_test_receiver` 8 times and `modal_dialog` 0. That is not a gap in the branch — `modal` is `el.matches(':modal')`, true only for the TOP LAYER, so it needs a `<dialog>` opened with `showModal()` or a fullscreen element, while the `<div role="dialog">` overlays most sites ship never enter the top layer and correctly arrive as `hit_test_receiver`. The branch stays, and `intercept_modal_backdrop.html` covers it; what the docs now say is that it is covered by a fixture and not yet seen in the wild, because "proven on the web" and "proven on a fixture" are different claims and this project does not get to blur them. `z_index` was `auto` on 7 of the 8 and on BOTH local fixtures, including a scrim that genuinely covers the page and a `<dialog>` in the top layer — stacking is usually DOM order plus `position`, and the top layer is not a z-index mechanism at all — so the docs point readers at `tag`/`id`/`class`, which named the receiver in every case measured (`div#scrim`, `dialog#terms`). The field is kept: `auto` is a true reading, and a page that does set a z-index is exactly where a reader would want it. It replaces the old `scrollIntoViewIfNeeded` + second `getBoxModel` dance, so the common path is one CDP call cheaper; an interception costs two more (a handle for the receiver, then `DOM.describeNode` for its uid — best effort, since scrims usually have no accessibility node). This closed two false successes that were indistinguishable from a real click: `click_overlay.html` reported `changed / focus_only` while `window.receiver === "scrim"`, and under `scroll-behavior: smooth` the box model was read mid-animation and the event went hundreds of pixels past the target — also `focus_only`. The probe scrolls with `behavior:'instant'` (what the selector path already did) and, if the aim point is still outside the viewport or still moving, retries 5×30 ms until two consecutive readings agree; NOTHING is dispatched either way, with a message that says so rather than "Clicked". **Convergence and the viewport are two facts, and collapsing them ordered an infinite loop** — the loop exited only on `in_viewport && agreed`, so a point that agreed with itself five times over while sitting off screen came out as `not_settled`, which is `unknown / scroll_not_settled`, which is the ONE rung whose `next` is `retry`. Measured on a consent wall: `(378, -14)` on seven attempts, three of them on a fresh profile, identical to the pixel, because the wall is `position: fixed` and the document's scroll is locked — `scroll` answers "Scrolled into view" and moves nothing. Confirmed on a second, independent site at `(-263.7, 107.5)` — negative x with y inside the viewport, where the first was a negative y — so the fixture carries both geometries and the classification reads the viewport rather than an edge. `classify` now takes `Settle::{Converged,Moving}` beside the probe: disagreeing readings are `not_settled` (transient, `retry` — the only reading that word now covers), and readings that AGREE about a point that cannot be aimed at are `off_target` → `unknown / aim_point_off_target` → `inspect`, whether the point is off screen or merely outside the element's own boxes. `Unaimable` carries which of the two it was, because the verdict is the same and the recovery is not: aim at a child with a box of its own, versus change the page state pinning the element off screen. Both shapes keep `next: inspect`; the vocabulary is unchanged, the classification is not (`tests/fixtures/fixed_wall_above_viewport.html`). `intercepted` ranks ABOVE `tree_delta` on purpose and the asymmetry is the point: the delta is a post-dispatch observation our own action can explain (the scrim's handler moves the page), while the interception is a pre-dispatch measurement it cannot. **A refusal carries what it measured** (`hit_test_report::Refused`): `--on-intercept refuse` used to answer `{"ok":false,"error":"Did not click uid=n208: div.gdpr-lmd-standard.gdpr-lmd-wall occupies the point…"}` and nothing else — no `hint`, which `hints.rs` promises every error carries, no `intercepted_by`, no `next`. The receiver had been measured, named, and then flattened into prose, so an agent had to parse an English sentence to learn what to close; and it was the SAFE mode that helped least, since `dispatch` returns the whole payload while the mode a caller picks precisely because it would rather re-plan than act returned the least to re-plan with. `Refused` rides through the error channel as `ElementError::Refused` — the route `commands::assert::NotHeld` already uses for exit 2 — and the three boundaries (`main`, `pipe::dispatch`, `pipe_dispatch::dispatch_single`) unpack it through `hit_test::refusal_in`, so all three answer with the same object: `delivery`, `uid`, `aim`, `intercepted_by`, `verdict`/`verdict_reason`/`next` from the same classifier every action uses, the specific `verdict_hint`, a `hint` under the `hints.rs` contract, and `dispatched:false`. `ok` stays `false` and the CLI still exits 1: nothing was dispatched, so the command did not do what it was asked. `next` is `dismiss` — the same token a dispatched interception gets, because `next` prescribes an action and the action is the same one, only safer here since the page saw no event. The hint's prohibition is rule 3 in its second flavour: a retry is not dangerous (nothing to double), it is FUTILE, so what is forbidden in words is repeating the command *while the receiver is there*. `dispatched:false` now rides on every response that aimed and sent nothing, refusal or not, and the `verdict_hint` on a refusal no longer says the receiver "received the event instead" — it received nothing either. The default `dispatch` keeps pointer semantics, because `elementFromPoint` matching the browser's real input hit test is evidence (12/12 on the design-record fixtures) and not equivalence — a wrong call should cost a warning, not the action. No claim at all is made when the target is inside an iframe (`depth > 0`): the frame's own document hit-tests cleanly while an overlay in the PARENT covering the `<iframe>` is invisible from there. `hover` and `drag` are out of scope and report `not_probed`; `--xy` names no element, so only "received by X" could ever be said there.
- **`--on-intercept guard` fills the gap between "always send" and "never send"** (`hit_test::{OnIntercept::Guard, should_refuse_intercept}`, `Hit::looks_inert`) — the gap was real, not hypothetical: a fifty-site audit measured a click aimed at lequipe.fr's `chrono` navigation link land on `BUTTON.Cmp__action.Cmp__action--yes`, text "oui, j'accepte", and `dispatch` (the default) sent the event through, accepting the site's GDPR wall on the caller's behalf — the delta showed the fourteen-node banner disappear. This is not the hit test being wrong: `elementFromPoint` measured the true receiver correctly, and dispatching to whatever a pointer would hit is the project's own documented choice. The gap is that nothing between `dispatch` and `refuse` asks the one question that matters — does the receiver DO anything — so `refuse` was the only way to stop it, and `refuse` would also have stopped on the five of eight receivers measured that day that were inert (`HEADER`, two text `DIV`s, an `IMG`, a search `iframe`). `Hit::actionable` answers the question inside the SAME probe call that already runs (no extra CDP round trip): a native interactive tag (`BUTTON`/`A`/`INPUT`/`SELECT`/`TEXTAREA`/`LABEL`/`OPTION`/`SUMMARY`), an ARIA interactive role, explicit keyboard focusability (`tabIndex >= 0`), or a `cursor: pointer` computed style. Two measured facts ruled out the alternatives: `modal` was `false` on all eight receivers (a CMP banner is a styled `<div>`, not a `<dialog>`, so `:modal` never matches it) and `z_index` was `auto` on seven of eight — neither carries the signal the classifier already special-cases them for. What DID let a person tell the two families apart on sight was `class` and `text` ("Cmp__action--yes", "oui, j'accepte") — deliberately NOT what the predicate uses: a keyword list of consent phrases across every language a wall might use is never complete, and is exactly the site-specific pattern-matching this project avoids everywhere else. `Hit::looks_inert` is `!iframe && !actionable` — an `<iframe>` refuses unconditionally, whatever `actionable` reads, because its content is opaque from here: cross-origin content refuses to answer at all, and same-origin would need a second execution context this probe does not open, which is a CDP call this project does not spend to resolve a case measured at one in eight. `tests/fixtures/intercept_iframe_overlay.html` pins the resulting asymmetry directly: its iframe holds one inert paragraph and `guard` refuses it anyway — an accepted false positive, not a missed true one, and the same "unknown leans toward caution" rule extends to no receiver being identified at all (`None`), which also refuses. The asymmetry is a stated choice, not an oversight: between a false refusal on an inert search box and a false dispatch into an unseen consent wall, this project accepts the former, because the caller can override a wrong refusal in one command (`--on-intercept dispatch`) while a wrongly-dispatched consent click cannot be undone by this tool. **The default stays `dispatch`.** `dispatch` is justified by its own measured record — 12/12 on the design-record fixtures, and checked separately across dozens of real sites — and `guard`'s predicate has no comparable record yet; flipping the default would also change behaviour far beyond consent walls, for every ordinary pair of overlapping buttons a script already clicks through today. A refusal under `guard` reuses the exact payload contract a `refuse` refusal has (`Dispatched::skipped(...).under(on_intercept)`, `Refused::to_json`/`text_lines`) rather than a second one: the two differ only in the words `refusal_message`/`report()`/`hints::intercepted_refusal_hint` choose once they read `on_intercept` off the response, naming "judged it a control" instead of hardcoding "refuse was set" — the fix that made a THIRD mode possible without a THIRD refusal contract.
- **A selector-targeted pointer action resolves ONE handle** (`hit_test::resolve_selector`) — `Runtime.evaluate` with `returnByValue:false`, then `DOM.describeNode` for the uid/role/name, then the probe and the dispatch through that same `objectId`. `click --selector` used to be three independent `querySelector` evaluations (pre-probe, action, post-probe) which a re-render between round trips could bind to three different nodes while the response described one. Same call count as before. `run_helpers::target_details` is no longer called on those paths — the action reports the node it actually probed and clicked.
